# 0002. GUI 자동 검증은 `--debug-cmd` 훅으로 한다 (합성 입력 금지)

- 날짜: 2026-08-05
- Phase: D0
- 상태: 채택
- 관련: CLAUDE.md 「검증 정책」, `docs/troubleshooting/synthetic-input-leak.md`

## Problem

트레이 상주 + 오버레이 앱은 **핵심 동작이 전부 GUI 이벤트에 묶여 있다.**
트레이 메뉴 클릭, 오버레이 버튼 클릭, 창 닫기 — 전부 사람 손이 필요하다.
그래서 D0 검증 절차 A~F 중 상당수가 "사용자가 직접 눌러보고 확인"으로 남았다.

수동 검증에만 의존하면:
- 회귀 확인이 매번 사람 시간을 태운다 (D1~D3 로 갈수록 누적)
- 재현이 안 된다 — "아까는 됐는데" 를 증명할 방법이 없다
- 개발자 본인이 1번 유저라 **검증 피로가 곧 도그푸딩 포기**로 이어진다

1차 시도로 `SendInput` 합성 입력을 썼다. **작동은 했지만 사고가 났다.**
창 검색이 사용자의 최소화된 메모장을 잡는 바람에 클릭이 화면 `(0,0)` 으로 가고,
타이핑이 사용자의 Chrome 으로, 이후 `Esc` 가 사용자의 Claude 앱으로 들어갔다.

근본 문제: **합성 입력은 어느 창에 도달할지 보장할 수 없다.**
포그라운드는 언제든 바뀌고, 좌표 기반 클릭은 그 순간 거기 있는 창이 먹는다.
사용자의 실제 작업 세션과 검증이 같은 데스크톱을 공유하는 한 안전하지 않다.

## Action

**앱 안에 검증용 진입점을 만든다.** 개발 빌드 전용 `--debug-cmd` 플래그로
명령 시퀀스를 받아, GUI 이벤트 핸들러를 **직접 호출**한다.

```powershell
pnpm tauri dev -- -- -- --debug-cmd "wait:4000,dump,start-session,wait:1500,dump,quit"
```

| 명령 | 대체하는 사람 동작 |
| --- | --- |
| `start-session` | 트레이 `▶ 작업 시작` 클릭 |
| `overlay-show` / `overlay-hide` | 트레이 `테스트 알림` / 자동 숨김 |
| `overlay-action:done\|snoozed\|skipped` | 카드 버튼 클릭 |
| `settings-open` / `main-show` / `main-hide` | 트레이 `설정` / 창 조작 |
| `quit` | 트레이 `종료` |
| `dump` | 눈으로 창 상태 확인 |
| `wait:<ms>` / `loop` | 대기 / 반복 |

설계상 중요한 선택 두 가지:

**1. 핸들러를 공유한다.** `start-session` 은 트레이 메뉴가 부르는
`tray::start_session_placeholder()` 를 **그대로** 호출한다.
훅 전용 코드가 따로 있으면 "훅은 통과하는데 실제 클릭은 실패"가 가능해져 검증이 무의미해진다.
`overlay-action` 도 마찬가지로 프론트엔드의 `dismiss()` 를 그대로 태운다.

**2. 프로세스 내 시퀀스로 한다.** 처음엔 "상주 앱이니 이미 떠 있는 인스턴스에
명령을 보내야 한다"고 보고 `tauri-plugin-single-instance` + argv 전달을 검토했다.
**전제가 틀렸다** — 검증은 우리가 프로세스를 띄우는 쪽이므로
한 수명 안에서 순서대로 실행하면 충분하다.
D3 범위인 single-instance 를 D0 로 당겨오지 않아도 됐다.

## Result

닫힌 항목:

| 항목 | 근거 |
| --- | --- |
| **F-1** 작업 시작이 로그만 찍는가 | `start-session` 전후 `dump` 가 완전히 동일 — 창 상태 변화 0 |
| **E-4** 트레이 종료가 프로세스를 끝내는가 | `quit` 후 `Get-Process hourstep-desktop` 결과 없음 |
| **B-4a** 액션 체인 | `done`/`snoozed`/`skipped` 각각 로그 + `overlay.visible` true→false |

릴리스 오염 없음 — 바이너리 바이트 스캔으로
`--debug-cmd` / `start-session` / `overlay-action` 문자열 **전부 미포함** 확인.

### 한계 (의도적으로 남김)

- **자기 프로세스 안에서만** 동작한다. 부팅 자동 실행으로 뜬 인스턴스에는 명령을 못 보낸다
- **"실제 마우스 클릭이 `WS_EX_NOACTIVATE` 창에 전달되는가"는 증명할 수 없다.**
  훅은 핸들러를 직접 부르므로 Win32 입력 경로를 타지 않는다.
  이건 Windows Sandbox / VM 격리 환경 E2E 의 몫으로 남긴다

즉 훅은 **"핸들러 이후"를 보증**하고, **"입력이 핸들러까지 닿는가"는 보증하지 않는다.**
이 경계를 문서에 명시해 두지 않으면 나중에 과신하게 된다.

## 대안 검토

| 대안 | 기각 사유 |
| --- | --- |
| `SendInput` 합성 입력 | 사용자 세션 침범 사고 발생. 도달 창을 보장할 수 없음 |
| single-instance 플러그인 + argv 전달 | D3 범위를 D0 로 당김. 프로세스 내 시퀀스로 충분했음 |
| 디버그 전용 named pipe / TCP | 같은 목적에 코드가 더 많고, 열린 포트/파이프라는 표면이 생김 |
| 환경변수 스크립트 (`HOURSTEP_SPIKE_AUTO_OVERLAY`) | 시작 시점 고정이라 시나리오를 못 짬. 실제로 이걸 쓰다 한계를 만나 대체함 |
| UI 자동화 프레임워크 (WinAppDriver 등) | WebView2 내부 접근이 불안정하고, 결국 합성 입력이라 같은 문제 |

## 영향

- 새 GUI 진입점(트레이 메뉴 항목, 카드 버튼)을 추가하면
  **`--debug-cmd` 에 대응 명령도 같이 추가**한다. 안 그러면 그 경로는 수동 검증으로 되돌아간다
- 검증 문서에 결과를 적을 때 **획득 방법**을 함께 남긴다
  (`상태 검사` / `캡처` / `--debug-cmd` / `격리환경`)
- `dump` 는 오버레이 표시 여부를 `overlay::is_visible()` 로 읽는다.
  `WebviewWindow::is_visible()` 을 쓰면 항상 false 다 — decisions/0001 과 같은 함정
