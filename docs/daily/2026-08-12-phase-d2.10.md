## 1. 동작 선택 (마이그레이션 v6)

새 `action_prefs` 테이블(`action_id TEXT PK, enabled INTEGER DEFAULT 1`), 8종(A1,A2,
B1~B4,C1,C2) 전부 켬으로 시드. 저장 위치를 `behaviors` 행이 아니라 별도 테이블로 둔
이유, 그리고 `actionAt`/`nextActionIndex` 가 8슬롯 고정 인덱스 공간 위에서 "꺼진 자리만
건너뛴다"는 방식을 고른 이유는 `docs/decisions/0014`.

핵심 함수 3개를 `src/core/actionRotation.ts` 에 추가:

- `enabledActionIds(prefs)` — 켜진 id 만 `Set` 으로
- `canDisable(prefs, id)` — **최소 1개 강제**의 판단 함수. "나 말고 켜진 게 있는가"만 본다
- `normalizeActionPrefs(raws)` — `normalizeBehaviors` 와 같은 성격의 신뢰 경계. 없는
  항목은 켬으로 채우고, `ROTATION_ORDER` 밖의 id 는 버리고, 전부 꺼진 손상 상태는 첫
  항목을 강제로 켠다

`actionAt`/`nextActionIndex` 는 `enabledIds` 를 선택 인자로 받도록 확장했다(기본값은
8개 전부 — D2.9 호출부는 코드 변경 없이 그대로 통과). vitest **19개**(기존 5개 +
14개, 스킵·최소1개·정규화·손상 케이스).

## 2. 동작 목록 화면

설정 창 「휴식 루틴」 섹션에 `[동작 목록 보기]` 토글을 추가했다(기존 「왜 이 주기인가요?」
바로 아래). 펼치면 8종 전체를 체크박스+이름+방법+시간+출처로, 상단에 원고 공통 고지문을
고정으로 보여준다. 마지막 하나 켜진 항목은 체크박스가 비활성화되고 옆에 "최소 1개는
켜져 있어야 해요" 태그가 뜬다(`canDisable` 결과를 그대로 UI 에 반영).

메인 창의 `ActionDetailCard`(D2.9, 오버레이 [자세히]가 여는 패널)와 방법·시간·출처
줄 구조가 완전히 같아서, `action-detail__*` 클래스를 `main.css` 에서 `components.css` 로
옮기고 `action-card__*` 로 이름을 바꿨다(레이아웃 지시자 `.action-detail`은 메인 창
전용이라 남겨 뒀다). 창이 갈려 있어 CSS 파일도 갈리지만(창별 엔트리) 내용 구조가 같은
건 한 곳에서 정의한다는 기존 원칙(`docs/design-system.md`) 그대로다.

## 3. 카운트다운 중 동작 안내

스트레칭 카드 [완료] → 카운트다운 전환 시 그 동작의 방법 전문(모든 줄)과 시간 문구를
보여준다. 눈휴식(D1)도 로테이션은 없지만 같은 자리에 고정 원고(`EYE_REST_METHOD`,
`EYE_REST_DURATION` — `strings.ts` 에 새로 추가, D1 원고를 그대로 복사)를 보여준다.
물(duration 0)은 카운트다운 자체가 없어 해당 없음.

창 확장/원복은 새 코드가 필요 없었다 — 기존 `fitWindow` 가 `phase` 전환마다 카드 실측
크기로 창을 다시 맞추는 로직을 D1 부터 갖고 있어서, 카운트다운 중 카드에 줄이 늘어나면
그 다음 `fitWindow` 호출이 자연히 창을 키운다. 근거·실측은 `docs/decisions/0014`.

### 시행착오 — 세션 1건이 실 통계에 섞였다가 지웠다

가장 처음 돌린 검증 스크립트는 `db-dump`/`action-prefs-dump`/`action-toggle` 을 `wait`
없이 연달아 호출했는데, 이게 전부 오버레이 웹뷰로의 비동기 이벤트 왕복이라 **도착 순서가
보장되지 않는다**는 걸 이번에 처음 확인했다 — 응답 로그 두 줄이 순서가 뒤바뀌어 찍혔다.
그 스크립트 안에 `start-session`/`done`/`end-session` 이 섞여 있어 세션 1건·완료기록 1건
(`🧘 스트레칭`, 몇 초)이 실 데이터에 그대로 남았다(`sessions` 12→13, `logs` 66→67).
이후 라운드부터는 (a) 상태를 바꾸는 명령 사이마다 `wait` 을 넣고 (b) 세션을 시작하지
않는 방식으로 바꿔 추가 오염을 막았다.

**후속 정리(같은 날, 사용자 확인 후):** 앱을 완전히 끈 상태에서 `work_sessions`/
`completion_logs` 를 직접 열어 확인했다. 사용자명에 한글이 들어 있어 `sqlite3.exe`
가 `%APPDATA%` 경로를 못 여는 문제가 있었고(ANSI 인자 처리 한계로 보인다), DB 를
ASCII 경로(`C:\Users\Public\...`)로 복사해 그 사본에서 작업했다. `started_at`·
`session_id`·`at` 을 대조해 스누즈 없이 3초 만에 시작·종료된 세션(`s-1786465875368`)
과 그 세션에 딸린 로그 한 줄(id=70, `stretch`/`done`)만 정확히 지웠다 — 그 직전
세션(87분짜리 실사용)과는 겹치지 않는다. 지운 사본을 원본에 덮어쓰고 앱 자체의
`--debug-cmd db-dump` 로 `sessions=12 logs=66` 복귀를 재확인했다(raw sqlite 조회가
아니라 앱이 정규화해서 읽는 경로로 재검증). 다음부터는 DB 를 건드리는 검증 전에
사본을 먼저 떠 두는 습관을 지킬 것 — 이번엔 사전 백업 없이 진행했다가 사후 수술로
해결했다.

## 설치본 갱신 — 0.4.0 → 0.4.1

버전을 `package.json`/`src-tauri/Cargo.toml`/`src-tauri/tauri.conf.json` 세 곳
모두 0.4.1 로 올렸다(D2.9 때 0.4.0 을 올린 방식 그대로 — 기능 추가폭에 비해 사소하다고
판단해 마이너가 아니라 패치로 묶었다). `pnpm build` → `pnpm tauri build` 로 NSIS/MSI
둘 다 만들고, `HourStep_0.4.1_x64-setup.exe /S` 로 기존 설치본 위에 무인 설치했다
(설치 전 실행 중이던 0.4.1 프로세스 없음 확인 — 설치 직전엔 이미 종료돼 있었다).
설치 후 실행해 `action_prefs` 테이블이 8행(전부 켬)으로 새로 생겼고 `sessions=12
logs=66` 는 그대로임을 DB 대조로 확인했다(마이그레이션 v6 가 기존 데이터를
건드리지 않고 새 테이블만 얹었다는 증거).
