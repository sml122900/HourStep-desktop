## 1. 작업을 방해하지 않는 데스크톱 오버레이 알림 구현

**Problem**
휴식 리마인더 앱의 알림이 작업 중 화면 위에 떠야 하는데, 알림이 **포커스를 뺏으면
타이핑이 끊겨** 제품 가치가 사라진다. Tauri v2 의 `WebviewWindow::show()` 는
Windows 에서 `ShowWindow(SW_SHOW)` 를 호출해 창을 활성화하며 포그라운드 포커스를 가져간다.
설정값 `focus: false` 는 창 **생성 시점**에만 적용되고 이후 `show()` 에는 무효였다.

**Action**
`windows-sys` 로 Win32 를 직접 호출해 표시 경로를 대체했다.
- `SW_SHOWNOACTIVATE` + `SWP_NOACTIVATE` — 표시할 때 활성화하지 않음
- `WS_EX_NOACTIVATE` — **클릭해도** 키보드 포커스가 넘어오지 않음 (마우스 이벤트는 정상 전달)
- `WS_EX_TOOLWINDOW` 추가 / `WS_EX_APPWINDOW` 제거 — 작업표시줄뿐 아니라 **Alt+Tab 에서도 제외**
  (`skipTaskbar` 설정만으로는 Alt+Tab 에 남는다)
- 매 표시마다 `HWND_TOPMOST` 재설정 — 전체화면 브라우저 등 다른 topmost 창 뒤로 밀리지 않게

**Result**
- `GetForegroundWindow` 실측: 카드 표시 전후 포그라운드 창 **불변**
  (Unity 에디터·Chrome 이 포그라운드인 상태에서 확인)
- 배치 실측: 1920×1080 주 모니터에서 `rect=(640,0) 640×240` → `(1920−640)/2 = 640`, 중앙·최상단 일치
- 확장 스타일 실측: `0x08000198` = `TOPMOST` + `TOOLWINDOW` + `NOACTIVATE`, `APPWINDOW` 해제
- Alt+Tab 후보 판정 알고리즘으로 **후보 아님** 확인 (같은 판정기로 메모장은 후보 → 판정 로직 자체 검증)
- 상주 메모리 약 **32MB** (Electron 대비 목표 달성)
- borderless 전체화면(F11) 위 표시 확인. **배타적 전체화면 게임은 미검증** — Windows 가
  topmost 를 억제하는 케이스로 알려져 있어 별도 대응 필요

**트레이드오프 (면접에서 물어볼 만한 지점)**
`WS_EX_NOACTIVATE` 는 키보드 포커스도 막아 Tab/Enter 로 버튼을 조작할 수 없다.
포커스 유지가 제품 정체성에 더 가깝다고 판단해 이쪽을 택했고,
접근성이 필요해지면 전역 단축키로 푸는 편이 맞다고 보았다.
코드에 `KEEP_FOCUS_ON_CLICK` 상수를 두어 판단을 뒤집을 수 있게 남겼다.

## 2. 프레임워크 상태 캐시 우회로 생긴 "보이지 않는" 버그 진단

**Problem**
오버레이 버튼을 누르면 로그는 정상이고 DOM 도 언마운트되는데 **창이 사라지지 않았다.**
투명 창이라 화면상으로는 정상인데, 화면 상단에 **눈에 보이지 않는 640×240 클릭 차단 영역**이 남아
그 자리의 다른 앱을 클릭할 수 없었다.
게다가 클릭한 적 없는 액션 로그가 찍혀서, 처음엔 합성 클릭 이벤트 문제로 오진했다.

**Action**
- 사람이 개입할 수 없는 조건(자동 트리거)에서 재현 → 액션 로그가 사라짐
  → **증상 두 개("유령 클릭 로그" / "창 미소멸")가 별개 문제**임을 분리
  (유령 클릭은 실제로 사람이 카드를 누른 것이었고, hide 실패 때문에 그렇게 보였을 뿐)
- 남은 단일 문제를 추적: tao 가 `WindowFlags::VISIBLE` 캐시를 두고 **상태 diff 만** Win32 에 적용.
  `ShowWindow` 를 직접 호출하면 캐시가 갱신되지 않아 이어지는 `hide()` 가
  "이미 숨김"으로 판단하고 **no-op** 이 되며 `Ok(())` 를 반환
- show 를 raw Win32 로 했으므로 hide 도 `ShowWindow(SW_HIDE)` 로 **대칭** 처리

**Result**
- 자동 검증으로 `IsWindowVisible` true→false 전환 확인
- 같은 뿌리의 함정을 한 번 더 예방: 이후 상태 조회에 `is_visible()` 을 쓰려다
  같은 이유로 항상 `false` 를 반환하는 것을 발견하고 Win32 직접 조회 함수를 분리
- 결정 기록(`decisions/0001`)과 코딩 규칙에
  "오버레이 창에 `show`/`hide`/`is_visible` 직접 호출 금지" 명시

**한 줄 교훈**
프레임워크의 상태 캐시를 우회할 거면 **쓰기만이 아니라 읽기 경로도 전부** 우회해야 한다.
한쪽만 우회하면 상태가 갈라지고, 에러 없이 조용히 실패한다.

## 3. GUI 데스크톱 앱의 자동 검증 체계 구축

**Problem**
트레이 상주 + 오버레이 앱은 핵심 동작이 전부 GUI 이벤트(트레이 클릭, 버튼 클릭, 창 닫기)에
묶여 있어 검증이 수동에 의존했다. 회귀 확인마다 사람 시간이 들고, 재현이 안 되며,
개발자 본인이 1번 사용자라 **검증 피로가 곧 도그푸딩 포기**로 이어질 위험이 있었다.

**Action**
검증 수단을 3층으로 나눴다.
1. **프로그램적 상태 검사** — `EnumWindows` / `GetWindowLongW(GWL_EXSTYLE)` /
   `GetForegroundWindow` / `WindowFromPoint` + `GetAncestor(GA_ROOT)` / `PostMessage(WM_CLOSE)`
2. **화면 캡처** — `Graphics.CopyFromScreen` 으로 렌더링 결과를 실제로 확인
3. **앱 내 디버그 훅** — 개발 빌드 전용 `--debug-cmd` 로 명령 시퀀스를 받아
   GUI 이벤트 핸들러를 직접 호출 (`start-session`, `overlay-action:done`, `quit`, `dump`, `loop` …)

훅 설계에서 중요했던 두 가지:
- **핸들러 공유** — 훅 전용 코드를 만들지 않고 트레이 메뉴가 부르는 함수를 그대로 호출.
  안 그러면 "훅은 통과하는데 실제 클릭은 실패"가 가능해져 검증이 무의미해진다
- **프로세스 내 시퀀스** — 처음엔 "상주 앱이니 실행 중 인스턴스에 IPC 를 보내야 한다"고 보고
  single-instance 플러그인 도입을 검토했으나, **검증은 프로세스를 띄우는 쪽**이므로
  한 수명 안에서 순서 실행하면 충분하다는 걸 확인하고 범위를 줄였다

**Result**
- 수동 검증 항목 중 다수를 자동화: 창 스타일·좌표·포커스, Alt+Tab 제외 판정,
  액션 3종(`done`/`snoozed`/`skipped`) 체인, 트레이 종료, placeholder 부작용 없음
- 부작용 없음을 **전후 상태 스냅샷 비교**로 증명 (`dump` → 동작 → `dump` 동일)
- 릴리스 오염 없음을 **바이너리 바이트 스캔**으로 확인
  (`--debug-cmd` / `start-session` / `overlay-action` 문자열 전부 미포함)
- 자동화 불가 항목을 명시적으로 분리: 재부팅, 지각 판단(눈에 보이는가),
  실제 마우스 클릭이 `WS_EX_NOACTIVATE` 창에 닿는가

**경계를 문서화한 이유**
훅은 **"핸들러 이후"만 보증**하고 **"입력이 핸들러까지 닿는가"는 보증하지 않는다.**
이 경계를 안 적어두면 나중에 과신하게 된다.

## 4. 자동화가 사용자 환경을 침범한 사고 → 정책과 도구로 차단

**Problem**
자동 검증에 `SendInput` 합성 입력을 사용했다. 검증은 통과했지만,
창 검색이 **이미 최소화돼 있던 사용자의 메모장**을 잡는 바람에
클릭이 화면 `(0,0)` 으로 가고 타이핑이 **사용자가 실제로 쓰던 브라우저와 다른 앱으로** 유입됐다.
근본 문제는 **합성 입력이 어느 창에 도달할지 보장할 수 없다**는 것 —
포그라운드는 언제든 바뀌고, 확인과 클릭 사이에도 바뀔 수 있다(TOCTOU).

**Action**
방어 코드로 막을 수 없는 문제라고 판단하고 **구조를 바꿨다.**
- **정책**: 사용자 데스크톱 세션에 합성 입력 주입 **금지**.
  클릭 수준 E2E 가 필요하면 Windows Sandbox/VM 격리 환경에서만
- **경계 정의**: 읽기 전용 수단(상태 검사·화면 캡처·창 메시지)은 계속 허용.
  단 캡처는 DWM 합성·하드웨어 오버레이 때문에 실화면과 다를 수 있어
  **"증거이지 최종 판정이 아니다"** 로 명시
- **대체 경로**: 클릭이 필요했던 시나리오를 `--debug-cmd` 훅으로 이전 (위 3번)
- **소급 처리**: 이미 금지된 방법으로 얻은 결과를 지우지 않고 **재검증 대상으로 표시**.
  이를 위해 검증 결과표에 **`방법` 열**을 추가

**Result**
- 합성 입력이 **필요할 이유 자체**를 제거 (금지만 하면 검증이 후퇴하므로 대체재를 먼저 만듦)
- 검증 근거의 **획득 방법 추적** 체계 도입 — 방법이 나중에 무효화될 때
  어떤 결론을 다시 세워야 하는지 가려낼 수 있음
- 정책을 프로젝트 규약 문서 최상위에 배치해 세션마다 읽히게 함

**한 줄 교훈**
검증 결과에는 "무엇을 확인했나"뿐 아니라 **"어떻게 확인했나"** 를 같이 남겨야 한다.

## 5. 오해를 부르는 빌드 오류의 역추적

**Problem**
`cargo check` 가 `error: linker 'link.exe' not found` 로 8개 크레이트에서 실패.
그런데 Visual Studio 2026 은 설치돼 있었고, `link.exe` 파일도 디스크에 실존했다.

**Action**
파일 존재 확인에서 멈추지 않고 설치 상태를 역추적했다.
- `vswhere` → VC++ 툴셋 컴포넌트는 선택됨
- VS `state.json` 의 `selectedPackages` → **`Windows11SDK` 계열이 하나도 없음**
- `Windows Kits\10\Lib` 디렉터리 부재, `kernel32.lib` 검색 0건 → 원인 확정
- winget 저장소에는 구버전 SDK 만 있어 부적합 → VS Installer 무인 수정으로 전환

**Result**
- 원인: **VC++ 컴파일러 툴셋과 Windows SDK 는 별개 컴포넌트**.
  툴셋만 있으면 `link.exe` 는 있지만 링크에 필요한 SDK 라이브러리가 없어
  rustc 의 링커 탐지가 실패하고 오해를 부르는 메시지를 낸다
- 부가 함정: `setup.exe --quiet` 는 UAC 승격을 스스로 하지 않아
  권한 없이 실행하면 종료 코드 **5007** 만 남기고 조용히 실패.
  설치 로그를 읽어야 이유가 나온다 → 처음부터 관리자 권한으로 실행
- README·프로젝트 규약에 "C++ 툴셋 + **Windows SDK**" 를 함께 요구사항으로 명시

## 6. 되돌아온 기술 부채를 "규칙"이 아니라 "테스트"로 막기 (디자인 시스템)

**Problem**
한 번 정리했던 UI 값이 세 Phase 만에 같은 상태로 돌아왔다. 색을 CSS 변수로 옮겨 두었지만
**규격 문서도 강제 장치도 없어서**, 창별 CSS 에 새 값이 계속 생겼다. 착수 시점 실측:
같은 성격의 버튼 **4벌**(창마다 다른 클래스), 반경 **8종**, 글자 크기 **12종**,
4px 격자를 벗어난 여백 다수. 라이트 모드를 손볼 때마다 네 군데를 따로 고쳐야 했다.
게다가 **텍스트 대비를 아무도 재 본 적이 없었다.**

**Action**
- 색·간격·반경·그림자·타이포·모션을 **토큰 한 파일**로 모으고(라이트/다크 두 벌),
  공통 컴포넌트 6종(Button / NumberField / Checkbox / Card / Section / EmptyState)으로
  네 벌로 갈린 버튼을 하나로 합쳤다
- **규칙을 사람에게 맡기지 않았다.** 이미 돌고 있는 vitest 에 CSS 를 문자열로 읽는
  가드레일을 얹어, 토큰 밖 색 리터럴·임의 px 여백·오버레이 그림자·두 테마 토큰 집합
  불일치를 실패로 만들었다
- 새 CSS 파일이 조용히 규칙 밖으로 빠지지 않도록 파일을 개별 import 하지 않고
  `import.meta.glob` 으로 훑고, **검사 대상 목록 자체를 테스트**로 고정했다
- WCAG 상대휘도 공식으로 팔레트를 **실측**해 실패 조합을 고쳤다

**Result**
- 대비 3건이 AA 본문 기준(4.5:1)을 넘도록 수정:
  다크 보조 텍스트 **3.68 → 5.08**, 라이트 **3.10 → 4.85**,
  주 버튼 위 흰 글자 **2.9 → 4.70** (세로 그러데이션을 단색 + hover 토큰으로 교체)
- 창별 스타일시트 3개 **886 → 606줄 (−32%)**. 총량은 거의 그대로다(1,003 → 1,023) —
  줄어든 만큼이 토큰·공통 컴포넌트 정의로 옮겨갔을 뿐이고, **줄 수가 목표가 아니라
  값이 한 곳에만 있는 것이 목표**였다 (설정 창 −41%, 메인 −27%, 오버레이 −20%)
- vitest 128 → **150개**. 가드레일이 실제로 실패하는지 일부러 위반을 넣어 확인
- 부수 효과로 **입력칸 버그 1건 발견·수정** — 이전 Phase 에서 고쳤던
  「마지막 글자를 지우면 값이 기본값으로 되돌아간다」가 다른 화면 한 곳에 그대로 남아 있었다.
  공통 컴포넌트로 통합하며 드러났고 정규화 함수를 순수 함수로 추출해 테스트로 덮었다

**트레이드오프 (면접에서 물어볼 만한 지점)**
stylelint 를 쓰지 않았다. 필요한 규칙이 네 개인데 그중 둘(테마 간 토큰 집합 일치,
특정 파일의 특정 토큰 금지)은 기성 규칙으로 표현되지 않아 어차피 커스텀이 필요했고,
의존성·설정 파일·실행 경로가 하나 더 느는 비용이 이득보다 컸다고 판단했다.
규칙이 열 개를 넘거나 팀이 커지면 전용 린터로 옮기는 게 맞다고 본다.

## 7. GUI 회귀를 잡는 스크린샷 검증 — "조용히 잘못된 결과" 세 종류

**Problem**
UI 리팩터링의 회귀는 단위 테스트로 안 잡힌다. 화면 8장(4화면 × 라이트·다크)을
자동 캡처해야 했는데, **사용자 데스크톱에 합성 입력을 주입하는 것은 프로젝트 규칙상 금지**라
클릭 없이 앱을 몰아 세워야 했다. 그리고 자동화가 세 번 연속 틀렸는데
**세 번 다 정상 종료하고 파일도 생겼다** — 결과를 눈으로 보기 전까지 알 수 없었다.

**Action**
실패마다 원인을 특정하고 설계를 바꿨다.
- **창을 못 찾음**: 자식 `powershell -File` 프로세스에서 창 열거 API 가 빈 결과를 준다
  (윈도 스테이션 격리). 예외가 아니라 빈 결과라 "아직 안 떴다"로 오해하기 쉽다
  → 호출 방식을 같은 프로세스 내 실행으로 변경
- **엉뚱한 창을 찾음**: WebView2 가 **같은 제목의 160×28 보조 창**을 띄운다
  → 같은 제목 중 면적 최대 창 선택 + 면적 하한
- **엉뚱한 순간을 찍음**: 메인 창이 **부팅 시점에 이미 보여서** 앵커가 거기 걸리고
  이후 시간표가 통째로 밀렸다 → 벽시계 스케줄을 폐기하고 **창 상태 전이 대기**로 재설계
  (보임→숨김→보임 3전이를 통과해야 앵커로 인정)
- 캡처 결과에 **픽셀 크기를 같이 출력**하게 해서 오탐이 로그에서 바로 드러나게 했다

**Result**
- 8장 전부 의도한 화면·의도한 테마로 캡처. 앱 빌드 시간이나 대기값이 바뀌어도 안 어긋난다
- **이 캡처가 실제 회귀를 검출했다** — 리팩터링으로 생긴 설정 창 가로 스크롤 넘침.
  기준선(`git stash` 로 변경 전 상태를 따로 캡처)과 비교해 "내가 만든 회귀"임을 먼저 확정한 뒤
  임시 계측 코드로 원인을 특정했다
- 함정 3종을 프로젝트 규약 문서에 요약해 다음 세션이 다시 밟지 않게 했다

**한 줄 교훈**
검증 자동화에서 가장 위험한 실패는 예외가 아니라 **빈 결과로 조용히 통과하는 것**이다.
같은 Phase 에서 두 번 밟았다(창 열거 0건 / CSS 를 빈 문자열로 읽는 lint 테스트).
그래서 두 곳 모두 **"검사 대상이 실제로 있는가"를 검사하는 테스트**를 따로 넣었다.

## 8. 겉보기 원인과 실제 원인이 달랐던 레이아웃 버그

**Problem**
공통 컴포넌트 도입으로 아이콘 버튼이 24→28px 커지자 설정 창에 가로 스크롤바가 생겼다.
그런데 산술이 안 맞았다 — 늘어난 폭은 16px 남짓인데 이름 입력칸은 `flex: 1 1 120px` 로
줄어들 여지가 충분했고, 실제로 줄지 않은 채 줄 전체가 넘쳤다.

**Action**
- 손으로 폭을 더해 보는 추정을 **버리고 계측**했다. 디버그 훅으로 앱 안에서
  `clientWidth` / `scrollWidth` / 각 요소 폭을 stdout 으로 찍었다
- `li=540`(할당 폭 497) — 이름칸이 안 줄어든 게 아니라 **줄이 들어갈 상자가 부풀어 있었다**

**Result**
- 원인은 버튼 크기가 아니라 **CSS Grid 의 암묵 트랙**이었다. `grid-auto-columns: auto` 의
  최대치는 `max-content` 라, 안쪽 `<input>` 들이 요구하는 기본 폭의 합만큼 트랙이 커지고
  **컨테이너보다 커져도 줄어들지 않는다.** 트랙 폭이 먼저 확정되므로 flex-shrink 는
  발동할 이유조차 없었다. 원래도 여유가 0에 가까웠고 리팩터링이 방아쇠였을 뿐이다
- `grid-template-columns: minmax(0, 1fr)` 로 트랙 최소를 열어 해결.
  계측으로 확인: `scrollWidth == clientWidth`. 덤으로 **창을 좁혀도 안 깨지게** 됐다
  (이전에는 max-content 아래로 반응하지 않았다)

**한 줄 교훈**
폭 문제는 계산하지 말고 재라. 계측 코드를 넣는 데 5분이면 되고, 겉보기 원인이
실제 원인과 다를 때 그 5분이 유일한 출구다.

## 9. 그럴듯한 버그 리포트를 그대로 고치지 않기 — 증상은 사실, 원인은 버전 스큐

**Problem**
사용자가 상세한 리포트를 냈다. 증상(입력칸에서 백스페이스가 안 먹고 값이 되돌아감),
비교 대상(같은 창의 다른 칸은 정상), 원인 추정("직전 작업에서 clamp 함수는 통일했지만
컴포넌트 교체는 안 됐다"), 수정 범위까지 적혀 있었다.
**추정이 그럴듯할수록 그대로 고치기 쉽고, 그러면 멀쩡한 코드를 "고치게" 된다.**

**Action**
고치기 전에 세 가지를 대조했다.
- **현재 코드**: 그 칸은 이미 공통 컴포넌트로 교체돼 있었다
- **커밋 이력**: `git log -S` 로 확인 — clamp 함수와 컴포넌트 교체가 **같은 커밋**이었다.
  보고서의 추정은 한 커밋 차이로 어긋난 것
- **설치 바이너리**: `VersionInfo.FileVersion` 이 두 Phase 뒤처진 버전.
  그 시점 소스를 `git show` 로 꺼내 보니 **보고된 코드와 정확히 일치**했고,
  "다른 칸은 정상"이라는 세부까지 그 버전의 상태와 맞았다

여기서 "이미 고쳐졌습니다"로 끝내지 않고, **왜 같은 버그가 두 번 났는지**를 물었다.
원인은 「빈칸·범위 밖은 값으로 확정하지 않는다」는 규칙이 **컴포넌트 안에만 있어
단위 테스트가 닿지 않았던 것**. 규칙을 순수 함수로 분리하고 회귀 케이스를 붙였다.

**Result**
- 코드 수정 0줄로 증상 해소(최신 빌드 설치). **동작을 바꾸지 않는** 리팩터링만 했다
- 규칙에 이름이 생겨 검색 가능해졌고, 회귀가 테스트로 고정됐다
- 새 테스트가 진짜로 잡는지 **뮤테이션으로 확인** — 함수를 망가뜨리면 4건이 실패
- 재발 방지를 프로세스로 남김: 리포트를 받으면 **설치본 버전 / 저장소 HEAD / 마지막 빌드
  시각**을 먼저 대조. 상태 문서 최상단에 "설치본이 어느 Phase 빌드인지"를 적어 둔다
  (실제로 그 줄이 이번 단서였다)

**면접에서 물어볼 만한 지점**
"보고자가 틀렸다"로 끝내지 않은 게 요점이다. 증상은 실재했고,
"직전 작업에서 뭔가 반쯤 하고 넘어갔다"는 감각도 맞았다 — 그 반쯤이 코드가 아니라
검증이었을 뿐이다. 리포트에서 **관찰(증상)과 추론(원인)을 분리해서** 관찰은 신뢰하고
추론만 재검증하면, 사용자를 부정하지 않으면서 진짜 결함에 도달할 수 있다.

**한 줄 교훈**
개발 PC 가 곧 사용 PC 면 "저장소 = 내가 쓰는 앱"이라고 착각한다.
그 둘은 빌드와 설치를 거쳐야 같아지고, 그 사이가 벌어진 기간이 곧 오진의 사각지대다.

## 10. "무조건 찍히는 로그"로 조건 오류와 이벤트 미발화를 분리한 프레임워크 버그 진단

**Problem**
창을 처음 숨길 때 시스템 토스트로 한 번만 안내하는 기능을 표준적인 방법
(`document.hidden`/`visibilitychange`) 으로 짰는데, `--debug-cmd` 자동 검증에서
**5초를 기다려도 로그가 한 줄도 안 찍혔다.** 조건문이 틀렸는지, 이벤트 자체가 안
오는지 구분이 안 되는 상태였다.

**Action**
- 대기 시간을 1초 → 5초로 늘려 재시도 — 타이밍 문제가 아님을 먼저 배제
- 리스너 안에 **조건 없이 무조건 찍히는 진단 로그**를 심어 재실행
  → 5초 넘게 한 줄도 안 찍힘. "조건이 틀렸다"가 아니라 **"이벤트 자체가 발화하지
  않는다"**로 원인 범위를 좁혔다
- 기존 코드에 같은 API 를 쓰는 자리(D2.5 의 tick 렌더 스킵)가 있었는데 왜 지금까지
  안 걸렸는지 되짚었다 — 그 자리는 **틀려도 표가 안 나는 자리**(성능 낭비일 뿐)였고,
  이번이 "숨었다는 사실 자체가 로직을 좌우하는" 첫 자리였다

**Result**
- 원인 확정: WebView2 는 Tauri 공식 `window.hide()` 로 숨긴 창에서 Page Visibility
  전환을 신뢰성 있게 주지 않는다(오버레이가 raw Win32 로 숨어 `is_visible()` 이
  어긋나는 문제, `decisions/0001`, 와 같은 결)
- Rust 가 창을 숨기는 지점에서 **명시적으로 이벤트를 쏘는** 구조로 재설계
  (`main://hidden`). X 닫기·버튼 두 경로를 함수 하나로 모으고, `--debug-cmd` 도
  같은 경로를 타게 맞춰서 검증이 실제 동작을 대변하게 했다
- 실 DB 대상 자동 검증: 첫 숨김 → 안내 1회, 같은 프로세스 안 재숨김 → 무음,
  **프로세스를 새로 띄운 뒤에도 무음**(플래그가 재시작을 넘어 지속). 세션·기록은
  만들지 않음을 전후 대조로 확인
- `CLAUDE.md` 에 "Page Visibility 는 신뢰할 근거가 못 될 때가 있다"는 경고를 남겨
  다음에 같은 API 를 로직 분기에 쓰려는 사람이 먼저 의심하게 했다

**한 줄 교훈**
"조건이 틀렸다"와 "이벤트가 안 온다"는 겉보기 증상(로그 없음)이 같다.
무조건 찍히는 로그 하나가 그 둘을 가르는 가장 싼 방법이었다.

## 11. 근거 없는 문구를 근거 있는 콘텐츠로 — 검증 가능한 상태로 옮겨 붙이기

**Problem**
행동 카드 문구가 "일어나서 1분 스트레칭할 시간이에요" 같은 임시 지시문이었다.
실제 연구·공공기관 근거를 연결해야 했는데, 세 가지가 동시에 걸려 있었다.
① 신체정보를 얼마나 수집해도 되는가(민감정보) ② 근거 원고 자체가 "동일 (…)" 같은
축약 표현을 쓰고 있어 원고를 그대로 옮기면 로테이션 순서상 맥락이 끊기는 조합이
생긴다 ③ 이미 실사용 중인 DB(개발자 본인이 도그푸딩)를 마이그레이션해야 한다.

**Action**
- **최소 수집 원칙을 스키마로 강제**: 체중 등은 애초에 열을 만들지 않았다.
  성별·연령대만 별도 `profile` 싱글턴 테이블에 — `settings` 의 불투명 JSON 에
  얹지 않고 열 단위로 분리해 향후 계정 동기화 때 그대로 옮길 수 있게 설계
  (`decisions/0012`)
- **원고 임의 수정 금지 규칙을 지키면서 문제를 보고**: 원고의 "동일 (…)" 이
  로테이션 순서(스트레칭 카드가 매 발화 다음 동작으로 도는 8종 순환)에서 가리키는
  대상이 안 맞는 조합을 발견했지만 스스로 고치지 않고 **우려로 지적**만 한 뒤,
  사용자가 준 수정본을 받아 콘텐츠 파일과 코드 상수 양쪽에 반영
- **상태를 어디 둘지 최소 침습으로 결정**: 로테이션 진행 인덱스는 세션·설정이
  아니라 "그 행동 자체의 사실"이라고 보고 `behaviors` 행에 열 하나만 추가
  (`duration_sec` 과 같은 결). 매 발화 도는 값이라 전체 저장 경로(방송 포함)를
  타지 않고 그 값 하나만 조용히 쓰는 별도 함수로 분리해 불필요한 재계산을 막았다
- **실 DB 대상 무영향 검증**: 세션을 시작하지 않은 상태에서 "테스트 알림" 경로로
  카드를 두 번 띄우고 닫아 로테이션 인덱스만 전진시키고(0→1→2), 세션·기록 테이블
  행 수가 검증 전후 정확히 같음을 대조해 부작용이 없음을 증명

**Result**
- vitest 17개 신설(물 참고 기준 10 + 동작 로테이션 7), 기존 스위트 178개 회귀 없음
- 마이그레이션(v4→v5) 이 실사용 데이터(세션 11건·기록 54건·행동 3종)를 전부
  보존함을 실측으로 확인
- 원고 수정 요청 1건을 "임의 수정" 없이 정확히 반영 — 콘텐츠 파일과 코드 상수
  두 곳을 동시에 갱신하고 관련 문서(daily log·STATUS)의 "우려 지적" 항목을
  해소로 갱신
- 버전을 올려 실제 설치본까지 재빌드·무인 설치(`/S`)하고, **컴파일된 번들 문자열을
  직접 grep** 해 소스 수정이 실제 배포물에 반영됐음을 증명(바이너리 자체는 프런트
  리소스가 압축돼 직접 grep 이 안 된다는 것도 확인하고 방법을 바꿈)

**트레이드오프 (면접에서 물어볼 만한 지점)**
로테이션 인덱스를 `behaviors` 행이 아니라 전역 설정 값 하나로 둘 수도 있었다
(구현은 더 단순했을 것). 그런데 미래에 다른 내장 행동도 로테이션을 쓸 수 있고,
그때 상태가 "행동에 속한 사실"이라는 모델이 깨지지 않게 지금부터 그 결을
따랐다 — 지금 당장 필요 없는 확장성에 열 하나를 미리 쓴 셈이라, 과설계로 볼
여지도 있다고 본다.

## 12. 새 기능에 새 리사이즈 코드를 안 짠 이유 — 기존 메커니즘을 먼저 의심하기

**Problem**
카운트다운 카드가 방법 전문·시간을 추가로 보여줘야 해서 카드 높이가 늘어나는데,
오버레이 창은 항상 **카드 실크기**여야 한다는 기존 원칙(투명 영역이 남으면 그만큼
클릭이 막힌다, D1)이 있었다. 요구사항만 보면 "카운트다운 상태에서 Win32
`SetWindowPos` 를 새로 호출해 창을 확장/원복하는 코드"가 필요해 보였다.

**Action**
새 코드를 짜기 전에 기존 리사이즈 경로(`OverlayWindow.tsx` 의 `fitWindow`)를 다시
읽었다. D1 부터 있던 이 함수는 **카드가 바뀔 때마다**(`useLayoutEffect` 의존성에
`phase` 가 이미 있었다) `getBoundingClientRect()` 로 실측해 창 크기를 다시 맞추고
있었다 — 즉 "표시할 내용이 커지면 창도 커진다"는 매커니즘이 이미 범용으로 존재했다.
그래서 카운트다운 중 카드 안에 방법·시간 줄을 그냥 더 그리기만 하고, 리사이즈
로직은 **한 줄도 추가하지 않았다.**

**Result**
- `--debug-cmd` 로 실측: 카드 단계 540×164 → [완료] 후 카운트다운 540×219(+55px,
  늘어난 줄 수만큼) → 카운트다운 종료 후 다음 표시에서 다시 540×164 로 원복
- 새 Win32 API 호출, 새 Tauri 커맨드, 새 capabilities 권한 전부 불필요 — 변경분이
  React 컴포넌트의 렌더 내용(JSX)에만 있어 리뷰·테스트 범위가 좁아졌다
- "클릭 차단 영역 = 카드 실크기" 라는 D1 의 불변식도 별도로 지킬 필요가 없었다 —
  측정-후-리사이즈 구조라 애초에 어긋날 수 없는 설계였기 때문

**한 줄 교훈**
요구사항에 "창을 키웠다 줄인다"가 들어 있다고 곧바로 새 리사이즈 코드를 떠올리지
않았다. 먼저 "이미 크기를 맞추는 코드가 있는가, 그 코드가 지금 언제 도는가"부터
물었고, 답이 "그렇다"였다.

## 13. 실 프로덕션 DB 에서 정확히 오염된 행만 골라 지우고, 앱 자신의 읽기 경로로 재검증

**Problem**
자동 검증(`--debug-cmd`) 스크립트가 비동기 명령을 `wait` 없이 연달아 보내는
바람에 응답 순서가 뒤바뀌었고, 그 여파로 개발자 본인이 실사용 중인 프로덕션
DB(도그푸딩 데이터)에 테스트 세션 1건·완료 기록 1건이 섞여 들어갔다. 지우려는
도구(`sqlite3.exe`) 는 사용자 프로필 경로에 한글이 있다는 이유로 파일 자체를
못 열었다.

**Action**
- 원인을 먼저 좁혔다: 셸 인코딩(Git Bash → PowerShell 교차 확인) 이 아니라
  **`sqlite3.exe` 자체의 인자 처리**임을 8.3 short path 시도(부분 실패)로 확인
- 앱을 완전히 종료한 상태에서 DB 를 ASCII 전용 임시 경로로 복사해 그 사본에서만
  작업 — 원본은 손대지 않고 사본에서 먼저 검증
- `started_at`/`session_id`/`at` 세 값을 대조해, 3초 만에 시작·종료된 세션과
  거기 딸린 로그 한 줄만 **정확히 특정**했다 — 바로 앞 세션(87분짜리 실사용
  기록)과 겹치지 않는지 먼저 확인한 뒤 지웠다
- 지운 사본을 원본에 되돌린 뒤, **raw SQL 조회가 아니라 앱 자체의 `--debug-cmd
  db-dump`(정규화 읽기 경로)** 로 다시 확인해 "내가 sqlite 로 본 값"과 "앱이
  실제로 읽는 값"이 같은지 이중으로 검증

**Result**
- `sessions=13→12`, `logs=67→66` — 오염 전 상태로 정확히 복귀, 그 직전의 실사용
  데이터는 전혀 건드리지 않음(대조 확인)
- 재발 방지를 코드가 아니라 **프로젝트 운영 규칙 문서**(`CLAUDE.md`)에 남겨
  다음 Phase 가 같은 실수를 반복하지 않게 함
- 두 함정(비동기 명령 순서 보장 안 됨 / `sqlite3.exe` 의 비ASCII 경로 처리)을
  각각 독립된 트러블슈팅 문서로 남겨, 다음에 비슷한 증상을 겪을 때 원인 후보를
  바로 좁힐 수 있게 함

**트레이드오프 (면접에서 물어볼 만한 지점)**
백업을 먼저 뜨지 않고 진행하다 사후 수술로 해결했다 — 원칙(다치기 전에 사본부터)을
알고 있었는데도 실전에서 건너뛴 경우다. "알고 있던 원칙을 실전에서 왜 건너뛰었는가"
라는 질문에는, 검증 스크립트가 원래 읽기 전용으로 설계됐다가 도중에 쓰기 명령이
섞여 들어간 걸 스스로 못 알아챈 게 근본 원인이라고 답할 수 있다 — 그래서 재발
방지책도 "백업해라"가 아니라 "쓰기 명령과 읽기 명령을 구분하고 순서를 보장해라"에
맞췄다.

**한 줄 교훈**
프로덕션 데이터를 실수로 건드렸을 때 중요한 건 "지웠다"가 아니라 "정확히 그것만
지웠다는 근거"다. 타임스탬프로 특정하고, 앱 자신의 읽기 경로로 재검증하는 두 단계가
없었다면 "아마 맞게 지웠을 것"이라는 추측만 남았을 것이다.
